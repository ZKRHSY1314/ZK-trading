# 90 天落地路线图：从"研究平台"到"每天真的会用的应用"

前提：先做完 `02_立即修复清单.md` 的 P0。P0 不做，下面每一步的测量结果都不可信。

---

## 先定义"能用"

现在这个项目缺的不是功能，是**一个每天都会发生、有始有终、结果会被记分的动作**。
先把产品定义收敛成一句话：

> **每个交易日 17:30 之前，给出一份 ≤10 只的排序清单；每一条都带买入触发条件、失效条件和仓位；
> 这份清单当天被冻结存档，1/3/5/10/20 个交易日后自动打分；首页永远显示最近 60 个决策日的
> 累计超额和胜率。**

这就是全部。没有屏幕监控、没有审批链、没有代码自演进。
判断项目是否"能用"的五条验收，全部围绕这一句：

| # | 验收 | 现在 |
|---|---|---|
| 1 | 一条命令启动，全绿，无需人工干预 | ⚠ 10 个进程，3 个 partial，1 个永久失败 |
| 2 | 每天自动产出当日清单，17:30 前完成 | ⚠ 最后一次运行是 2026-07-19，已停 6 周 |
| 3 | 每条建议都被冻结存档并自动打分 | ✅ forecast ledger 已具备（这是项目最大的资产）|
| 4 | 首页显示累计胜率/超额，而不只是清单 | ❌ 完全没有 |
| 5 | 回测跑的代码路径 = 当日清单的代码路径 | ❌ 两套完全不同的实现 |

**第 5 条是全部工作的核心。** 做到它，项目就活了；做不到，再加十个子系统也还是原地打转。

## Phase 1（第 2–4 周）：一条链路

### 1.1 定下唯一的候选定义

保留 **`app/candidates/selection_v2.py`** 作为唯一打分实现（它已经在给 forecast ledger 供数，
是唯一有测量记录的那条）。其余全部退场：

- `RuleEngine` + `dengzhan.py` → **不删，改造成 selection_v2 内部的一个特征提供者**
  （灯盏信号是有价值的先验，但不能是第二套并行打分器）。
- `full_market_scan.py`、`auto_discovery`、`offhour.py` 的潜力搜索 → 降级为**候选池召回**，
  只负责"哪些股票进入打分"，**不产生分数、不产生排名**。
- 召回 / 打分 / 定价 三段职责分离，任何一段都不许再有第二套实现。

### 1.2 回测与实盘共用同一段代码

这是 Phase 1 的核心交付。目标形态：

```python
# app/signals/pipeline.py   —— 唯一入口，回测和当日清单都调它
def score_universe(as_of: date, bars: BarSource, fundamentals: FundamentalSource) -> list[ScoredCandidate]
```

- `BarSource` 在实时路径下读 `daily_bar_cache`，在回测路径下读**同一张表但截断到 `as_of`**。
- 回测引擎**不再自己造 MarketSnapshot**（现在的 `engine.py:300` `_snapshot()` 整个删掉），
  改为调用 `score_universe`。
- 判定标准：**给定同一个 `as_of`，回测产出的 Top-N 必须与那天线上产出的 Top-N 完全一致**。
  写一个测试锁死这件事，用 forecast ledger 里已有的 6 个历史决策日做回放对拍。

> 这个测试（"回放对拍"）是整个项目最值得写的一个测试。它一旦绿了，
> 你之后每一次策略调整都能立刻知道历史上会发生什么。

### 1.3 数据补到 2018

- 现在只有 2024-04 → 2026-07（2.3 年，且已过期 6 周）。`DENGZHAN_BACKTEST_SPEC.md` 要 8 年，是对的：
  2.3 年只覆盖了一种市场状态，任何在这段上调出来的参数都是过拟合。
- 用现成的 `backfill_market_universe.py --apply --days 2000` 分批回填。
- 顺手合并两个库：`market_history.sqlite3` 的 `daily_bars` 和 `trading_local.sqlite3` 的
  `daily_bar_cache` 是同一份数据的两份拷贝（2,597,860 vs 2,615,763 行，约 2GB 重复）。
  **留一份，另一份改成视图。**
- 同时补 `symbol_fundamentals_daily`（P0-1 建的表），否则灯盏规则在回测里依然废。

**Phase 1 出口**：回放对拍测试通过 + 日线覆盖 2018 起 + 只剩一个打分实现。

## Phase 2（第 5–8 周）：诚实地测

有了 Phase 1，第一次可以做真正的实验。**这一阶段不写新功能，只跑实验、只出报告。**

### 2.1 实验设计（照抄 `DENGZHAN_BACKTEST_SPEC.md`，它写得很好）

```
训练窗   2018-01 → 2022-12
验证窗   2023-01 → 2024-06     ← 只在这里调参
封存窗   2024-07 → 2026-08     ← 全程不许看，最后只看一次
Walk-forward: 12 个月训练 / 3 个月前推，滚动
```

**铁律：封存窗只能看一次。** 看第二次就等于用它调参了，结论作废。
把这条写进 `AGENTS.md`，让 Codex 也遵守。

### 2.2 必须先跑的三个基线（否则任何结果都没有参照）

1. **随机基线**：每天随机选 10 只，同样的执行模型和费用。
2. **反向基线**：把当前 `final_score` 取负号排序。
   —— 按第 1.3 节的 IC 测量，这个基线**很可能跑赢正向**。必须跑，结果必须记录。
3. **单因子基线**：只用 `drawdown_from_250d_high`（当前 IC 最高的正向特征，+0.256）排序。

> 如果完整的 selection_v2 打不过"单因子基线"，那 2372 行打分代码就是负资产。
> 这个对照必须做，而且要有心理准备接受它。

### 2.3 样本量门槛

- **≥ 300 笔独立交易**，跨 ≥ 3 个市场状态，才允许说"有 / 没有正期望"。
- 少于 300 笔时，报告里只许写 `insufficient_data`。
  （项目已经有这个词，`forecast_evaluations` 里 502 条 stock 评估就是这个状态 —— 保持这份诚实。）

### 2.4 关键：多尺度 IC，不要只看 1 日

现在只标注了 h=1（1074 条）和 h=3（30 条），h=5/10/20 **全是 0 条**。
而 1 日尺度上 A 股短期反转占主导，动量因子负 IC 是常见现象 ——
**这不代表灯盏策略错了，可能只是尺度错了。**

灯盏策略的语义是"低位涨停 → 1–5 日回踩 → 加仓 → 持有到分歧"，天然是 **5–20 日** 的东西。
Phase 2 必须先把 h=5/10/20 的 outcome 标注补齐（数据已经在库里，只是没跑 feedback），
再下任何结论。**有可能 IC 在 h=5 就翻正了 —— 这是当前最值得先验证的一个假设。**

### 2.5 Phase 2 的出口是一个判断，不是一个功能

跑完之后必须写一份两页结论，只回答一个问题：

> **在 2018–2024 训练+验证窗上，当前打分函数在哪个持有周期上有统计显著的正超额？没有就是没有。**

- **有** → 进 Phase 3，把它产品化。
- **没有** → 也进 Phase 3，但产品定位改成"**结构化观察 + 记分板**"：
  系统不再声称能选股，只负责"帮你把想法冻结、执行、自动打分"。
  **这依然是一个有价值、能用的应用**，而且是现有基建最擅长的事。
  这个 fallback 必须提前接受，否则 Phase 2 的结论会被无意识地美化。

## Phase 3（第 9–12 周）：砍与发

### 3.1 砍

按 `02_立即修复清单.md` 的 P2 执行完：`backend/app` < 50k 行、路由 < 200、单文件 < 1500 行、
前端删掉 25k 行死代码。**目标不是"整洁"，是让你一个人还能拿住它。**

### 3.2 发

交付这四个界面，不多不少：

1. **今日清单**：≤10 只，每条含 触发价 / 止损价 / 失效条件 / 仓位 / 三条理由 / 数据新鲜度。
2. **记分板**（当前完全缺失，也是最该补的）：最近 60 个决策日的累计超额、胜率、
   Precision@5、Rank IC 曲线，按 h=1/5/20 分开显示。**首页第一屏就是它，不是清单。**
3. **单票复盘**：某只票从进入候选到出场的完整事件流（`monitoring_events` 已有数据结构）。
4. **规则台**：改 `rules.yaml` 的阈值，立刻看到"如果这样改，过去两年会怎样"（依赖 Phase 1 的回放对拍）。

### 3.3 一条不能破的运行纪律

从 tag `v1.0` 起，写进 `AGENTS.md`：

> **新增任何子系统，必须同时下线一个同等体量的旧子系统；
> 新增任何打分逻辑，必须先在封存窗之外证明它提升了 Rank IC。**

这条纪律是这个项目现在最需要的东西 —— 过去 12 个月的问题不是能力不够，是没有闸门。

## 最后一句

这个项目已经把最难的部分做完了 —— **point-in-time 不可变账本、逐笔执行模型、
不许用未来数据的门禁、review-only 边界**。这些东西绝大多数个人量化项目一辈子都没有。

它现在缺的只是：**把这套基建对准一个具体的信号，然后接受它给出的答案。**

先修回测。其余都在后面。
