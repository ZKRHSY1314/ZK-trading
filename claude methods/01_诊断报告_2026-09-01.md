## 结论先行

这个项目的**工程基建是同类个人项目里少见的扎实**：point-in-time 账本、T+1/涨跌停/手续费执行模型、
forecast feedback、数据质量门禁、进程身份校验、review-only 不变量、542 个测试 77 秒全绿、CI 可用。

但它目前**不是一个可用的应用**，原因不是工程质量，而是三件事：

1. **唯一被测量过的信号是反向的**（Rank IC = −0.17，Top5 次日超额 −2.25%）。
2. **回测在结构上不可能产生任何一笔交易**（39 次回测全部 0 笔成交），所以过去没人能发现第 1 条。
3. **同时存在至少 5 条互不相通的选股链路**，被度量的那条不是界面展示的那条，也不是回测的那条 —
   反馈永远回不到策略上。

一句话：**基建在为一个从未被验证过的信号服务，而且验证通道是断的。**
要变成能用的应用，接下来该做的不是加功能，是把这三条接通、然后诚实地面对结果。

## 一、被测量过的信号，方向是反的

### 1.1 系统自己算出来的评估

`forecast_evaluations` 表里唯一一条 `status='ready'` 的记录（stock / horizon=1 / 36 folds）：

```
spearman_rank_ic  = -0.16930981
precision_at_k(5) =  0.35555556
coverage          =  0.29586777
sample_count      =  1074
rank_predictor    = "negative_rank_then_score"
target            = "benchmark_neutral_return>0"
```

其余 502 条 stock 评估和 131 条 sector 评估全部是 `insufficient_data`。

### 1.2 我独立重算的分层收益（join forecast_decisions × forecast_outcomes，n=1104）

| 排名档 | 样本数 | 次日基准中性超额（均值） | 胜率 |
|---|---:|---:|---:|
| **Top 5** | 180 | **−2.251%** | 35.6% |
| 6–10 | 177 | −0.663% | 49.2% |
| 11–20 | 357 | **+0.413%** | 42.6% |
| 21+ | 360 | −0.086% | 38.1% |
| 全体 | 1104 | −0.599% | 39.9% |

**排名越靠前，表现越差，且单调。** 这不是噪声形态，是系统性反向。

### 1.3 反向的来源：所有动量特征在 1 日尺度上都是负 IC

对 `features_json` 里每个数值特征算 Spearman IC（vs 次日基准中性超额，n=1074）：

| 特征 | IC |
|---|---:|
| ma5_slope | **−0.403** |
| ma20_slope | −0.346 |
| ma10_slope | −0.258 |
| pct_change | −0.238 |
| price_percentile_250d | −0.153 |
| upper_shadow_ratio | −0.117 |
| **drawdown_from_250d_high** | **+0.256** |
| bounce_from_250d_low | +0.146 |
| final_score（综合分） | **−0.178** |

`selection_v2` 的打分是"越强越高分"，而 1 日尺度上 A 股短期反转占主导，于是综合分 IC 直接是负的。

### 1.4 必须说清楚的边界

- 样本只有 **6 个决策日**（2026-07-12 → 2026-07-19），**一个市场状态**，**只标注了 h=1**（h=3 只有 30 条，h=5/10/20 全是 0）。
- 所以这**不能**证明"灯盏策略无效"。它只证明两件事，而这两件事已经足够重要：
  1. **当前上线的评分函数，在唯一有数据的尺度上没有正期望，符号还是反的。**
  2. **系统已经具备发现这件事的能力，但没有任何流程去看它。** 这是最该修的。
- 本报告只陈述对你自己数据库的统计测量，不构成任何投资建议。

## 二、回测在结构上不可能成交（39 次运行，0 笔交易）

`historical_backtest_runs` 最近 6 次：

```
id=39  2025-10-15 → 2026-06-29  completed  initial=100000  final=100000
       total_return=0.0  trade_count=0  closed_trade_count=0
（34–38 同样，全部 0）
```

`historical_backtest_trades` / `historical_backtest_closed_trades` 两张表**都是空的**，
但 `historical_backtest_daily_equity` 有 6915 行 —— 即"每天都在记录一条纹丝不动的净值曲线"。

### 根因（已复现，两处叠加）

**根因 A：回测快照缺 `pb` / `market_cap_billion`**

- [`app/backtest/engine.py:300`](../backend/app/backtest/engine.py) `_snapshot()` 只从 `daily_bar_cache` 构造
  MarketSnapshot，**从不设置 `pb` 和 `market_cap_billion`**（日线缓存里也没有这两列）。
- [`app/strategies/dengzhan.py:44`](../backend/app/strategies/dengzhan.py) 在 `market_cap is None`
  且 rules.yaml 配了市值上下限时，直接 `return False, "缺少总市值数据，无法确认市值要求"`。
- `configs/rules.yaml` 恰好配了 `min_market_cap_billion: 50 / max_market_cap_billion: 200`。

⇒ `dengzhan_low_position_limit_up` 在回测里**永远 False**。

**根因 B：tier 门槛数学上要求两条策略规则同时命中**

- [`app/rules/engine.py`](../backend/app/rules/engine.py) `_normalized_score`：分数 = raw / max_strategy_weight × 100。
- 正权重只有 `dengzhan_low_position_limit_up`(25) + `dengzhan_forced_divergence`(20) = 45。
- `strong_min_score: 80` ⇒ 需要 raw ≥ 36 ⇒ **只有 45（两条全中）才够**。中一条 25 → 55.6 分，中一条 20 → 44.4 分，都是 rejected。
- 而 `app/backtest/engine.py:180` 的建仓条件是 `decision.tier == CandidateTier.strong`。

⇒ A 让第一条永久失效，B 让"只中第二条"永远不够格 ⇒ **上限 44.4 分，永远 rejected，永远 0 成交。**

### 复现（实跑结果）

构造一根"完美灯盏 K 线"（价/250日高=0.33、涨停 10%、量比 2.0、5 日涨幅 3%），
按回测 `_snapshot()` 的字段集合喂给 RuleEngine：

```
PERFECT BAR (as backtest builds it): score=44.44  raw=20.0  max=45.0  tier=rejected
    constitution_no_high_position   True   0.0  | 当前价/高点=0.33，符合低位要求
    dengzhan_low_position_limit_up  False  0.0  | 缺少总市值数据，无法确认市值要求   ← 根因 A
    dengzhan_forced_divergence      True  20.0  | 量比 2.00 达到强制分歧阈值
    risk_no_chasing_after_big_rise  True   0.0  | 未触发大涨后追高风控

SAME BAR + pb/market_cap: score=100.0  tier=strong                                ← 补上两个字段即通
```

**这是整个项目最高优先级的单点缺陷**：它让"策略有没有用"这个问题在过去所有时间里都无法被提问。
更糟的是回测 `status` 仍然返回 `completed`——0 笔成交被当成成功。

## 六、这个项目真正的病

不是代码质量差，是**反馈回路被"再加一个子系统"替代了**。

每次遇到"效果不明确"，项目的应答都是新增一层：screen_monitoring → trade_execution_gateway →
dataset2 审批链 → sim_cockpit → agent_control → public_opinion → full_market_scan → codex_decision_review。
每一层都写得很规范、都有测试、都 review-only、都不产生可证伪的结论。

而唯一能证伪的两条路——**回测**和**forecast ledger**——一条从来没成交过，一条算出了负 IC 却没人消费。
