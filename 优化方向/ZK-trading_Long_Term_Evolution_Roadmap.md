# ZK Trading 长期演进路线图：Codex、交易软件、本地大模型与自动交易闭环

> 适用对象：Codex / 开发代理 / 项目维护者  
> 项目方向：A 股 AI 交易驾驶舱 → 交易经验学习系统 → 受控代码进化系统 → 高时效数据系统 → 人审实盘执行 → 风控笼子内的自动交易  
> 核心原则：先复盘，再学习；先模拟，再小资金；先人审，再自动；任何 AI/Codex 都不能绕过风控和实盘权限边界。

---

## 1. 长期愿景

未来希望将 `ZK-trading` 从一个本地模拟交易与复盘系统，逐步演进为一个能够与 Codex、本地大模型、行情数据、交易软件共同进化的交易操作系统。

最终愿景包括：

1. 软件可以监控电脑实时屏幕，识别交易软件状态。
2. 软件可以在安全边界内进行实盘操作，最终完成自动交易。
3. Codex 不只是代码助手，而是交易软件的长期监督者、复盘者和进化者。
4. 系统每日复盘交易结果，把经验写入记忆库。
5. Codex 定期分析软件运行结果，发现策略、数据、代码、风控中的不足。
6. Codex 根据复盘结果提出代码修改、策略调整和架构优化建议。
7. 所有策略和代码改动必须经过测试、回测、模拟盘、人审后才能进入更高权限环境。
8. 后期可以配备多种高效可行的交易策略，由 Codex 监督、评估、改进。
9. 数据接口逐步升级，最终达到秒级市场响应。
10. 新电脑上部署本地大模型，并通过统一模型接口接入交易软件。

这个方向可以做，但不能从当前阶段直接跳到“Codex 控制券商软件自动实盘交易”。必须分阶段、分权限、分验证层推进。

---

## 2. 当前阶段判断

当前项目已经具备：

- 候选池扫描。
- 规则引擎。
- 模拟交易骨架。
- 历史回测骨架。
- AI 参数提案骨架。
- 组合风控与市场环境初步判断。
- 前端驾驶舱面板。
- 明确的 simulation-only 安全边界。

但当前项目还不适合直接进入实盘自动交易阶段。

当前更合理的下一步是：

```text
V2.0：让模拟结果、回测结果、复盘结论变得可信。
```

只有当系统能可靠回答“过去做得对不对、哪里错、为什么错、改了之后有没有变好”，后续 Codex 才能安全地参与代码进化和策略进化。

---

## 3. 总体阶段路线

| 阶段 | 核心目标 | 是否可以让 Codex 改代码 | 是否可以接本地模型 | 是否可以实盘 | 是否可以屏幕控制 |
|---|---|---:|---:|---:|---:|
| V2.0 | 可信回测、可信模拟、可信复盘 | 否，只能规划/小修 | 否，仅预留接口 | 否 | 否 |
| V2.5 | 交易经验记忆库 | 否，只能生成建议 | 可设计接口 | 否 | 否 |
| V3.0 | Codex 受控代码进化闭环 | 可以，但只能生成 patch/PR | 可辅助分析 | 否 | 否 |
| V3.5 | 本地大模型接入 | 可以，仍需人审 | 是 | 否 | 否 |
| V4.0 | 高时效数据与事件驱动架构 | 可以 | 是 | 否 | 否 |
| V4.5 | 屏幕只读监控 | 可以 | 是 | 否 | 只读 |
| V5.0 | 交易执行网关与人审实盘 | 只能改非实盘核心或经强审查 | 是 | 小资金、人审 | 可 dry-run |
| V6.0 | 风控笼子内的自动交易 | 可以，但不得自批上线 | 是 | 可控自动 | 可控执行 |

## 4. 阶段详细规划

---

# V2.0：可信回测与可信模拟

## 4.1 目标

V2.0 的核心不是“更聪明”，而是“更诚实”。

所有后续自动学习、AI 调权、Codex 修改代码、策略进化，都依赖一个前提：

```text
系统必须准确知道过去的信号、交易、模拟和回测到底表现如何。
```

如果回测和模拟盘本身不准，Codex 学到的就是假经验。

---

## 4.2 V2.0 应完成的能力

### 4.2.1 修正回测成交模型

需要增强：

- 涨停一字板无法买入。
- 跌停一字板无法卖出。
- 支持部分成交。
- 支持成交额/成交量流动性上限。
- 买入金额不能超过当日成交额的一定比例。
- 高开/低开触发止盈止损时，使用保守成交价。
- 每笔交易记录 `fill_status`：
  - `full`
  - `partial`
  - `rejected`
  - `blocked_by_limit`
  - `blocked_by_liquidity`

### 4.2.2 修正盈亏指标

当前应改为按真实平仓交易计算：

- `realized_pnl`
- `win_rate`
- `avg_win`
- `avg_loss`
- `profit_loss_ratio`
- `expectancy`
- `max_consecutive_losses`
- `average_holding_days`
- `exposure_ratio`

每次买入应生成 position lot，卖出时按 FIFO 或平均成本匹配。

### 4.2.3 增加基准比较

每次回测至少比较：

- 上证指数。
- 沪深 300。
- 后续可加中证 1000。

指标包括：

- 策略收益。
- 基准收益。
- 超额收益。
- 策略最大回撤。
- 基准最大回撤。
- 交易次数。
- 空仓比例。
- 平均持仓天数。

### 4.2.4 补全组合风控

需要真正实现：

- 单日最大亏损限制。
- 最大回撤停止开仓。
- 连续亏损冷却。
- 总仓位上限。
- 单票仓位上限。
- 弱势大盘仓位减半。
- 极端风险环境禁止新开仓。

并接入：

- `SimulationPlanner`
- `BacktestEngine`
- `MonitoringService`
- 前端风控面板

### 4.2.5 每日复盘报告

系统每日应输出：

- 今日扫描了多少股票。
- 进入强候选、观察候选、剔除名单的数量。
- 哪些股票触发提醒。
- 哪些提醒后来表现好。
- 哪些提醒失败。
- 失败原因分类：
  - 数据问题
  - 规则问题
  - 买点太早
  - 追高
  - 风控未拦截
  - 市场环境恶化
  - 人工未执行计划
- 今日模拟收益。
- 今日最大浮亏。
- 今日最大回撤。
- 今日规则贡献度。
- 明日观察列表。

---

## 4.3 V2.0 进入下一阶段的条件

进入 V2.5 前必须满足：

```text
- 每笔信号都有后续结果。
- 每笔模拟交易能追踪盈亏。
- 回测指标可信。
- 模拟成交规则更接近真实市场。
- 缺失数据不会被系统当成有效信号。
- 每天可以生成复盘报告。
- 风控拦截有日志和原因。
```

# V2.5：交易经验记忆库

## 5.1 目标

建立长期交易经验记忆库，让软件能够积累每日复盘结果，并为 Codex 后续分析、策略改进、代码进化提供数据基础。

记忆库不是简单文本，而应分层存储。

---

## 5.2 记忆库分层设计

### 5.2.1 原始事件库

记录不可篡改的原始事件：

- 扫描记录。
- 候选池变化。
- 监控提醒。
- 模拟下单。
- 人工操作。
- 告警确认。
- 加入剔除名单。
- 加入复盘列表。
- 后续价格走势。
- 数据质量状态。

### 5.2.2 复盘结论库

记录每日/每周/每月复盘结论：

- 成功案例。
- 失败案例。
- 买早案例。
- 追高失败案例。
- 风控拦截正确案例。
- 风控漏拦案例。
- 主力出货识别案例。
- 低位强势成功案例。
- 低位强势失败案例。

### 5.2.3 策略表现库

记录策略维度的表现：

- 哪条规则贡献正收益。
- 哪条规则经常误报。
- 哪个市场环境下策略失效。
- 哪个市场环境下胜率更高。
- 哪类股票更适合该策略。
- 哪类股票需要剔除。
- 策略收益、回撤、胜率、盈亏比的长期变化。

### 5.2.4 代码进化库

记录 Codex 参与进化的过程：

- Codex 提出过什么问题。
- Codex 提出过什么修改计划。
- 修改影响了哪些模块。
- 自动测试是否通过。
- 回测结果是否改善。
- 样本外验证是否改善。
- 是否被人工接受。
- 是否进入模拟盘。
- 是否被回滚。

---

## 5.3 V2.5 中 Codex 的权限

Codex 可以：

- 读取复盘结果。
- 总结失败原因。
- 提出规则修改建议。
- 提出代码修改建议。
- 生成 patch 草案。
- 生成开发任务文档。

Codex 不可以：

- 自动合并代码。
- 自动修改实盘配置。
- 自动改变交易权限。
- 自动扩大仓位。
- 自动调用券商软件。
- 自动点击交易按钮。

# V3.0：Codex 受控代码进化闭环

## 6.1 目标

让 Codex 进入“代码进化闭环”，但所有修改必须处于受控状态。

V3.0 的目标不是让 Codex 自主控制实盘，而是：

```text
让 Codex 基于复盘数据发现软件缺陷，提出修改，生成 patch，通过测试和回测验证，再交由人工确认。
```

---

## 6.2 代码进化闭环流程

标准流程：

```text
1. 系统每日收集交易和模拟结果。
2. 系统生成每日复盘报告。
3. Codex 读取复盘报告和交易经验库。
4. Codex 找出策略/代码/数据/风控缺陷。
5. Codex 生成修改计划。
6. Codex 生成代码 patch 或 PR。
7. 自动运行后端测试。
8. 自动运行前端构建。
9. 自动运行历史回测。
10. 自动运行样本外验证。
11. 系统生成改动影响报告。
12. 人工确认后合并。
13. 合并后进入模拟盘观察期。
14. 模拟盘稳定后，再考虑更高权限。
```

---

## 6.3 V3.0 安全规则

必须遵守：

```text
- Codex 不得直接修改 live_trading_enabled。
- Codex 不得新增真实下单接口。
- Codex 不得存储券商账号、密码、Cookie、Token、API key。
- Codex 不得绕过风控规则。
- Codex 不得自己批准自己的代码上线。
- Codex 只能在分支、patch 或 PR 中修改代码。
- 所有策略修改必须经过回测和样本外验证。
- 所有实盘相关修改必须人工审批。
```

---

## 6.4 V3.0 验收条件

```text
- Codex 能根据复盘报告提出修改计划。
- Codex 能生成可审查 patch。
- patch 自动运行测试。
- patch 自动运行回测。
- 系统能比较修改前后指标。
- 不改善或风险变大的 patch 自动拒绝。
- 人工审批前不会进入主分支。
```

# V3.5：本地大模型接入

## 7.1 目标

在新电脑上部署本地大模型，并通过统一模型接口接入交易软件。

本地大模型主要负责：

- 复盘总结。
- 相似案例检索。
- 策略失败归因。
- 代码改进建议。
- 参数调整建议。
- 风险解释。
- 交易计划解释。
- 多策略对比总结。

---

## 7.2 统一模型接口

建议新增：

```text
backend/app/ai/model_gateway.py
```

接口设计：

```python
class ModelGateway:
    def analyze_signal(self, context: dict) -> dict:
        ...

    def summarize_daily_review(self, context: dict) -> dict:
        ...

    def propose_parameter_change(self, context: dict) -> dict:
        ...

    def review_risk(self, context: dict) -> dict:
        ...

    def review_code_patch(self, context: dict) -> dict:
        ...
```

Provider 支持：

```text
disabled_provider
mock_provider
openai_provider
qwen_provider
local_llm_provider
```

---

## 7.3 本地模型安全边界

本地大模型可以：

- 解释信号。
- 总结复盘。
- 检索相似案例。
- 提出策略改进建议。
- 提出参数调整建议。
- 提出代码改进建议。

本地大模型不可以：

- 直接发出真实下单。
- 绕过风控。
- 直接修改 `rules.yaml`。
- 直接修改 `live_trading_enabled`。
- 直接控制券商软件。
- 直接扩大实盘仓位。
- 读取或存储券商账号密码。

# V4.0：高时效数据与事件驱动架构

## 8.1 目标

逐步升级行情数据接口，提高系统对市场变化的响应速度，最终向秒级响应靠近。

注意：

```text
秒级响应不是简单把轮询频率调高，而是整个系统架构都要升级。
```

---

## 8.2 V4.0 需要完成

- 更稳定的行情源。
- 秒级或准实时行情接口。
- 行情缓存层。
- 异步任务队列。
- 事件驱动引擎。
- 限流控制。
- 失败降级。
- 网络异常处理。
- 行情延迟统计。
- 数据质量监控。
- 秒级信号 replay。
- 实时信号去重。
- 同一秒多信号排序。
- 高峰期性能压测。

---

## 8.3 V4.0 安全边界

V4.0 只做：

```text
秒级监控、秒级提醒、秒级模拟。
```

仍然不直接做：

```text
秒级实盘自动下单。
```

---

# V4.5：屏幕只读监控

## 9.1 目标

让系统能够监控电脑实时屏幕，识别交易软件状态。

但 V4.5 只能做只读监控，不能点击交易软件。

---

## 9.2 屏幕监控能力

第一阶段能力：

- 截屏。
- OCR/视觉识别。
- 识别交易软件是否在线。
- 识别持仓。
- 识别委托。
- 识别成交回报。
- 识别账户资金。
- 识别弹窗异常。
- 识别网络异常。
- 与系统内部账户状态对账。
- 异常时提醒人工。

---

## 9.3 为什么先只读

屏幕自动化很脆弱，可能出现：

- 按钮位置变化。
- 弹窗遮挡。
- 软件卡顿。
- 网络断开。
- 验证码。
- 交易软件升级。
- 鼠标焦点错误。
- 窗口被覆盖。
- 显示缩放变化。
- 多屏幕坐标偏移。

所以 V4.5 的目标是：

```text
确认交易软件看到的状态 = 系统记录的状态。
```

不是直接下单。

# V5.0：交易执行网关与人审实盘

## 10.1 目标

引入真实交易执行能力，但必须通过中间网关，不允许 Codex 或模型直接控制券商软件。

建议新增：

```text
Trade Execution Gateway
```

---

## 10.2 Trade Execution Gateway 职责

它负责：

- 接收交易意图。
- 检查账户状态。
- 检查交易时间。
- 检查涨跌停。
- 检查持仓。
- 检查现金。
- 检查单日亏损。
- 检查单票仓位。
- 检查总仓位。
- 检查连续亏损冷却。
- 检查是否需要人工授权。
- 生成订单预览。
- 等待人工确认。
- 执行订单。
- 记录完整审计日志。
- 异常时自动熔断。

---

## 10.3 Codex 在 V5.0 的权限

Codex 只能发出交易意图，不得直接执行。

示例：

```json
{
  "intent": "buy",
  "symbol": "SH600000",
  "reason": "strong_candidate_with_clean_risk",
  "max_amount": 3000,
  "stop_loss": 9.80,
  "risk_level": "low",
  "requires_human_confirm": true
}
```

Execution Gateway 决定：

- 能不能做。
- 做多少。
- 是否需要人工确认。
- 是否触发熔断。
- 是否禁止。
- 是否降级为观察。

---

## 10.4 V5.0 必备安全设施

必须具备：

- 一键停止。
- 自动熔断。
- 单日亏损上限。
- 单票仓位上限。
- 总仓位上限。
- 连续亏损冷却。
- 所有订单审计日志。
- 操作截图/录像留痕。
- 人工确认开关。
- 只读模式切换。
- 最小资金实盘沙盒。
- 异常自动切回模拟/只读模式。

---

# V6.0：风控笼子内的自动交易

## 11.1 目标

在长期模拟、小资金实盘、人审执行验证稳定后，才考虑进入 V6.0。

V6.0 不是“Codex 自由控制交易软件”，而是：

```text
Codex 在风控笼子内辅助自动执行。
```

---

## 11.2 V6.0 系统结构

```text
Codex / 本地大模型
        ↓
策略建议 / 代码补丁 / 交易意图
        ↓
Evolution Module
        ↓
Backtest + Paper Trading + Risk Review
        ↓
Human Approval
        ↓
Trade Execution Gateway
        ↓
Broker API Adapter / Screen Control Adapter
        ↓
真实交易软件
```

---

## 11.3 执行适配器优先级

优先级应为：

```text
Broker API Adapter > Screen Control Adapter
```

屏幕控制可以保留，但应作为最后选择。  
如果券商或交易软件支持稳定 API，应优先使用 API，不优先使用鼠标键盘模拟点击。

---

## 11.4 V6.0 进入条件

必须满足：

```text
- 实盘小资金长期稳定运行。
- 每次下单都有审计记录。
- 每次异常都能自动暂停。
- Codex 改代码不会直接影响实盘。
- 策略更新必须经过回测、模拟、人审。
- 屏幕控制经过大量 dry-run 测试。
- 交易软件升级/弹窗/断线都有处理方案。
- 一键熔断和只读模式可用。
- 人工能随时接管。
```

---

# 12. Evolution Engine 设计

## 12.1 模块目标

建议未来新增：

```text
Evolution Engine
```

它是软件与 Codex 共同进化的核心模块。

目标：

```text
交易结果 → 复盘 → 经验沉淀 → 缺陷分析 → 修改计划 → 代码 patch → 回测验证 → 人审上线
```

---

## 12.2 子模块设计

### 12.2.1 Experience Recorder

记录每日交易经验：

- 信号。
- 候选池。
- 监控告警。
- 模拟交易。
- 人工操作。
- 后续走势。
- 失败原因。
- 成功原因。
- 数据质量。

### 12.2.2 Review Generator

自动生成：

- 每日复盘。
- 每周复盘。
- 每月复盘。
- 策略表现报告。
- 风控表现报告。
- 数据质量报告。

### 12.2.3 Weakness Analyzer

分析不足：

- 策略缺陷。
- 代码缺陷。
- 数据缺陷。
- 风控缺陷。
- 前端操作缺陷。
- 人工执行偏差。

### 12.2.4 Patch Planner

让 Codex 生成修改计划：

- 修改目标。
- 影响模块。
- 风险点。
- 测试要求。
- 回测要求。
- 回滚方案。

### 12.2.5 Safe Code Evolution

Codex 生成代码 patch，并自动运行：

- Python compile。
- pytest。
- 前端 TypeScript check。
- Vite build。
- 回测。
- 样本外验证。
- 风控验证。
- 安全扫描。

### 12.2.6 Promotion Gate

决定修改能否升级：

```text
draft → tested → backtested → paper_approved → human_reviewed → simulation_enabled → live_candidate
```

但任何进入实盘的变化都必须人工审批。

---

## 12.3 Evolution Engine 总规则

```text
所有进化都必须可回滚。
所有修改都必须有原因。
所有修改都必须有测试。
所有策略变化都必须有回测。
所有实盘相关变化都必须人工确认。
Codex 永远不能自己给自己批准上线。
模型输出永远不能直接改实盘配置。
```

# 13. 未来系统最终形态

最终系统应形成闭环：

```text
行情数据
   ↓
策略判断
   ↓
候选池
   ↓
盘中监控
   ↓
模拟 / 人审实盘 / 自动执行
   ↓
交易结果
   ↓
每日复盘
   ↓
经验记忆库
   ↓
Codex / 本地大模型分析不足
   ↓
策略改进 / 代码改进 / 风控改进
   ↓
回测验证 / 模拟验证 / 样本外验证
   ↓
人工审批
   ↓
安全上线
```

---

# 14. 当前最应该给 Codex 的任务

当前不要让 Codex 做实盘控制。  
当前应该让 Codex 设计并实现 V2.0-V2.5 的基础能力。

## 14.1 推荐任务一：V2.0 可信回测与模拟

可以直接给 Codex 的任务：

```text
请基于当前 ZK-trading 项目设计并实现 V2.0 可信回测与可信模拟增强。

目标：
1. 增强历史回测成交模型。
2. 修正交易配对、realized_pnl、win_rate、profit_loss_ratio、expectancy 等指标。
3. 增加基准比较。
4. 增加组合风控：max_daily_loss、max_drawdown_stop、consecutive_loss_cooldown。
5. 每笔信号与模拟交易都能被后续复盘追踪。
6. 每日生成复盘报告，为 V2.5 交易经验记忆库做准备。

安全边界：
- 不得启用 live_trading。
- 不得新增真实下单接口。
- 不得新增券商控制能力。
- 不得存储账号、密码、API key、Cookie。
- 不得让 AI 或 Codex 绕过风控。
- 所有交易能力仍保持 simulation-only。

验收：
- 后端 compileall 通过。
- pytest 通过。
- 前端 vue-tsc 与 vite build 通过。
- 回测 fixture 能验证涨跌停、部分成交、流动性限制、T+1、费用、印花税、滑点。
- 新增指标计算有单元测试。
- 风控 gate 有单元测试。
- 生成 V2.0 handoff 文档。
```

---

## 14.2 推荐任务二：V2.5 交易经验记忆库设计

```text
请为 ZK-trading 设计 V2.5 交易经验记忆库。

目标：
1. 设计原始事件库。
2. 设计复盘结论库。
3. 设计策略表现库。
4. 设计代码进化库。
5. 设计每日复盘写入流程。
6. 设计 Codex 读取复盘结果并生成修改建议的接口。
7. 所有内容保持 review-only / simulation-only。

要求：
- 使用当前 SQLite 存储风格。
- 不接入实盘。
- 不新增券商控制。
- 不存储敏感凭证。
- 预留未来向向量数据库迁移的接口。
- 生成 schema、service、API、测试和文档。
```

# 15. 总结

长期目标可以概括为：

```text
V2.0：软件会诚实复盘。
V2.5：软件会积累交易经验。
V3.0：Codex 会受控改进软件。
V3.5：本地大模型接入软件。
V4.0：系统有高时效数据。
V4.5：系统能只读监控屏幕。
V5.0：系统具有人审实盘能力。
V6.0：Codex 在风控笼子里辅助自动执行。
```

当前最重要的不是实盘，也不是屏幕控制，而是：

```text
先把每日复盘、经验记忆库、Codex 代码进化闭环设计出来。
```

只有这个基础打牢，未来接本地大模型、秒级行情、屏幕监控、实盘执行，才不会变成不可控风险。
